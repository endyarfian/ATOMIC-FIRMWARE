# A.T.O.M. V1.9.5 — Hybrid MQTT Design

## Baseline and branch

- Immutable source baseline: branch `v1.9.4`.
- Development branch: `v1.9.5-hybrid-mqtt`.
- Target board: ESP32-S3 DevKitC-1 N16R8.
- Arduino-ESP32 Core target recorded by the project README: 3.3.0.
- This document records the implementation design. It does not claim that firmware compilation or hardware validation has passed.

## Required behavior

A.T.O.M. shall prefer the local broker over plain MQTT/TCP when it is reachable, and fall back to MQTT over WSS when the local broker cannot be reached.

1. LAN transport: `mqtt://192.168.0.128:1883`.
2. Internet transport: `wss://mqtt.endyarfian.web.id:443/mqtt`.
3. Both transports use the existing device credentials configured in Admin Mode.
4. Client ID remains `ATOMIC-001`.
5. Existing topic names, JSON payloads, event identifiers, and heartbeat cadence must remain unchanged.
6. The server-side Node.js subscriber remains connected to `mqtt://127.0.0.1:1883`; no server-side MQTT changes are required for this firmware feature.

## Source findings in V1.9.4

- MQTT is implemented with PubSubClient over WiFiClient.
- Broker host, port, username, and password are stored in Preferences namespace `atomicmqtt`.
- Admin configuration is handled by `POST /api/mqtt/configure`.
- `mqttPublishJson()` is the shared publication path for heartbeat, events, sessions, and operators.
- `updateMqtt()` currently owns connection retry and heartbeat scheduling.
- MQTT publications are QoS 0 and are not persisted for later replay when offline.

## WSS transport implementation direction

PubSubClient + WiFiClient does not implement the WebSocket upgrade/framing required by the public WSS endpoint. Do not change the port to 443 while retaining the existing transport.

Evaluate Espressif ESP-MQTT (the ESP-IDF MQTT client) as the transport implementation because ESP-MQTT supports TCP and WSS URI schemes. Arduino-ESP32 Core 3.3.0 is based on ESP-IDF 5.5, but the Arduino build must explicitly verify that the ESP-MQTT headers and component symbols are exposed by the selected board package before replacing the existing MQTT implementation.

TLS certificate verification must remain enabled. Do not use `skip_cert_common_name_check`, insecure TLS, or an empty trust configuration as a shortcut. Prefer the ESP-IDF certificate bundle if it is available in the Arduino build; otherwise document and pin a suitable CA certificate.

## Hybrid connection state machine

- Start with the LAN TCP endpoint.
- Give each connection attempt a bounded timeout; do not block the main loop for a long interval.
- If LAN cannot connect, stop the current attempt cleanly and try WSS.
- If WSS cannot connect, retry with bounded backoff and periodically retry LAN so the device returns to the preferred local route when it comes back into range.
- Avoid rapid route flapping: require a successful LAN reachability probe and a minimum dwell interval before switching from an active WSS connection to LAN.
- On Wi-Fi loss, mark MQTT disconnected and let the existing Wi-Fi reconnect process recover independently.
- MQTT connection callbacks must not perform blocking network operations or peripheral work.

## Compatibility requirements

Preserve:
- Device ID `ATOMIC-001` and MQTT client ID `ATOMIC-001`.
- Username/password from the existing `atomicmqtt` NVS namespace.
- Topics:
  - `atomic/devices/ATOMIC-001/heartbeat`
  - `atomic/devices/ATOMIC-001/events`
  - `atomic/devices/ATOMIC-001/sessions`
  - `atomic/devices/ATOMIC-001/operators`
- Existing payload schemas and event types, including ignition, access, session, and operator events.
- 30-second heartbeat cadence.
- Existing Admin Mode, fingerprint, relay, ignition, RTC/NTP, and sleep behavior.

## Admin Mode configuration and NVS migration

Do not reinterpret the existing single broker host/port fields as both LAN and Internet endpoints. Introduce explicit transport configuration with safe defaults:
- LAN host/port default to `192.168.0.128:1883`.
- WSS host/port/path default to `mqtt.endyarfian.web.id:443/mqtt`.
- Hybrid mode is the default for new firmware.
- Reuse existing MQTT username/password; never display or return the password from status endpoints.
- Read legacy `host` and `port` keys without deleting them. A migration must preserve the saved username/password and allow an operator to continue using an explicitly selected custom LAN broker if needed.

The Admin page must show the active transport and connection state, and allow a controlled LAN/WSS configuration without exposing credentials.

## Validation checklist

1. Compile with the exact Arduino-ESP32 Core 3.3.0 and ESP32-S3 N16R8 board settings.
2. Boot with existing V1.9.4 NVS data; verify Wi-Fi, RTC, operators, and MQTT credentials remain intact.
3. At the Homelabs LAN, verify LAN TCP is selected and heartbeat is received.
4. Outside the LAN, verify WSS connects through Cloudflare Tunnel and heartbeat is received.
5. Return to LAN; verify the device eventually prefers LAN without connection flapping.
6. Interrupt Internet and restore it; verify reconnect without blocking fingerprint, ignition, relay, OLED, or Admin Mode.
7. Verify access events, ignition events, session start/end, and operator upsert/delete retain their existing topics and payloads.
8. Verify TLS certificate validation rejects an invalid certificate.
9. Verify the server subscriber and dashboard require no configuration changes.
